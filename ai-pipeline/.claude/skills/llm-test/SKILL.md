# LLM pipeline：测 → 改 → 再测

目标：$ARGUMENTS（为空就先问我）

整个过程只在 `evals/` 里写文件，不改项目源码。

## 约定

- 测试文件 `evals/<slug>.<ext>`：一个目标一个文件，长期保留当回归；同一目标重跑时整个覆盖；不用测试框架会自动收集的文件名。
- 开头注释两行：运行命令（参数是每条输入的重复次数）和 `prompts: <名字>, …`，列出它覆盖的 prompt。
- 候选 prompt 按 prompt 放，不按场景放：`evals/_candidates/<VARIANT>/<名字>.txt`，名字取 prompt 所在的模块或节点。这个目录是临时的，不进 git。
- 环境变量 `VARIANT`：`base` 用源码原样；其他值从 `evals/_candidates/<VARIANT>/` 读，有对应文件的 prompt 整体替换，没有的保持源码。所以任何测试文件都能跑任何候选。
- 已有测试文件不符合这些约定时，顺手迁移（只改加载路径和开头注释，用例不动）。

## 准备

1. 读代码：有哪些节点、哪些调 LLM、state 结构、数据流、LLM 配置从哪读。
2. 选能暴露问题的最低一层，告诉我选哪层、为什么：
   - 确定性代码：普通单元测试。
   - 单个 LLM 节点：构造输入 state 直接调用。
   - 单轮切片：串起相关节点跑一轮，跳过无关节点。
   - 端到端：只为多轮流程用完整 graph，可让另一个 LLM 扮演用户。
3. 写测试文件，先写进项目再运行：
   - 自包含。用例 = (名字, 输入 state/历史, 几种说法, 判定)，覆盖目标的正向、边界、拒绝/跳过/提问/换语言，以及这个 prompt 的其他主要职责。
   - 说法要多样，只用于测试，不能进 prompt。判定只查关心的点：结构化输出精确比较，文本用正则，必要时用 LLM 裁判（只回 PASS/FAIL）。判定误报就修判定。
   - 每条跑 N 次（默认 3–4），限并发，对限流和解析错误重试；失败时打印输入、输出和上游中间结果。
4. 找回归：grep `evals/` 里 `prompts:` 与本次可能改动的 prompt 有交集的其他文件。

## 循环

1. **测**：新文件和回归文件都用 `base` 跑，记下基线。确认问题能复现，每条失败归因为 prompt / 上游节点 / 判定。
2. **改**：在 `evals/_candidates/<版本>/` 写候选，可以多个版本。每个候选都是对整个 prompt 的重新设计：
   - 通读全文，把新行为融进它该在的位置，合并重叠、删掉过时的规则；行为跨节点时，相关 prompt 一起设计，放在同一版本目录。
   - 简短、分节清楚（角色 / 输入 / 决策规则 / 输出 / 示例，按需取舍），每条规则只说一次，不写套话和重复强调，示例每类一个。
   - 改动涉及新的 prompt 时，回到准备第 4 步补找回归并跑基线。
3. **再测**：同一个 `VARIANT` 跑新文件和全部回归文件。主场景 ≥ 95% 且每个回归文件不低于基线算稳定；不稳就回到第 2 步。三轮仍不稳就停下来汇报并问我。

## 交付

1. `evals/_candidates/` 只留选中的那个版本，删掉其余的。
2. 汇报，不动源码：
   - 源码怎么改：每个文件、每个 prompt 变量换成哪个候选文件的内容，再加上设计思路（新 prompt 怎么组织、跟旧的比改了什么、为什么）。
   - 通过率表：每个测试文件 × (base / 各候选 / 选中)，新旧 prompt 长度，剩余失败及归因。
   - 改完后怎么验证：新文件和回归文件用 `VARIANT=base` 的运行命令，结果应该和选中候选一致；通过后删掉 `evals/_candidates/`，测试文件留着当回归。

修改这个 skill 本身时也一样：整体重写，不打补丁。
